# Internationalization

Components generate some text on their own: accessible names (the `aria-label` of close buttons, pagination, carousel…), default placeholders, empty states and the month and day names of `MsDatePicker`. That text comes from a typed dictionary, `MsMessages`.

| Language   | Dictionary       | Picked by                       |
| :--------- | :--------------- | :------------------------------ |
| Portuguese | `msMessagesPtBR` | default, or any `pt-*` `locale` |
| English    | `msMessagesEn`   | `en`, `en-US`, `en-GB`…         |
| Spanish    | `msMessagesEs`   | `es`, `es-ES`, `es-MX`…         |

Text props still win over the dictionary: `placeholder`, `emptyText`, `confirmLabel` and the like override the message for that instance only.

## Switching the language

App-wide, with the plugin:

```ts
import { createApp } from "vue";
import { createMsI18n } from "@magic-style/vue";

createApp(App)
  .use(createMsI18n({ locale: "en-US" }))
  .mount("#app");
```

Or for part of the tree, with `MsProvider`. Nested providers inherit the locale from their ancestor:

```vue
<MsProvider locale="es-ES">
  <slot />
</MsProvider>
```

`locale` is a BCP 47 tag. The language (the part before `-`) picks the dictionary, and the full tag goes to `Intl`. That's why `MsDatePicker` month and weekday names come out right even when there is no dictionary for the language: `fr-FR` uses Portuguese strings but French dates.

## Laravel + Inertia

Share Laravel's locale from `HandleInertiaRequests`, swapping `_` for `-` (`pt_BR` becomes `pt-BR`):

```php
public function share(Request $request): array
{
    return [
        ...parent::share($request),
        'locale' => str_replace('_', '-', app()->getLocale()),
    ];
}
```

Then pass it to the layout's provider. Since `usePage().props` is reactive, the locale follows every Inertia visit:

```vue
<script setup lang="ts">
import { computed } from "vue";
import { usePage } from "@inertiajs/vue3";
import { MsProvider } from "@magic-style/vue";

const page = usePage<{ locale: string }>();
const locale = computed(() => page.props.locale);
</script>

<template>
  <MsProvider :locale="locale">
    <slot />
  </MsProvider>
</template>
```

The full setup, with `createMsI18n` in the client and SSR entries, is in [Laravel + Inertia](/guide/laravel-inertia).

## Tweaking strings

`messages` takes partial overrides. Only the keys you pass change:

```vue
<MsProvider
  locale="en-US"
  :messages="{ select: { empty: 'Nothing found' }, dialog: { close: 'Close window' } }"
>
  …
</MsProvider>
```

The plugin takes the same shape: `createMsI18n({ locale: "en-US", messages: { … } })`.

## Adding a language

Start from an existing dictionary. The `MsMessages` type makes you fill in every key:

```ts
import { createMsI18n, msMessagesEn, type MsMessages } from "@magic-style/vue";

const fr: MsMessages = {
  ...msMessagesEn,
  locale: "fr-FR",
  select: { ...msMessagesEn.select, placeholder: "Sélectionner...", empty: "Aucun résultat" },
  // …
};

app.use(createMsI18n({ locale: "fr-FR", messages: fr }));
```

Some messages are functions, because they depend on values. For example `carousel.slide(index, total)`, `datePicker.nextDays(days)` and `select.create(query)`.

## In your own components

`useMsMessages()` reads the same dictionary as the nearest provider:

```vue
<script setup lang="ts">
import { useMsMessages } from "@magic-style/vue";

const messages = useMsMessages();
</script>

<template>
  <button type="button" :aria-label="messages.dialog.close">×</button>
</template>
```

The full list of keys is in the `MsMessages` type, exported from `@magic-style/vue`.
